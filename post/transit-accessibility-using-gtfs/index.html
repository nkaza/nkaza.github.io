Transit Accessibility Using GTFS

Last updated on Nov 8, 2026 25 min read transportation, R

Introduction

Understanding the reach and effectiveness of public transit is important to understand how urban environments are accessible for different groups of people. Analysing fixed route public transit has become relatively straightforward with the introduction of the “General Transit Feed Specification,” a common standard for transit agencies to publish their schedules. Pioneered by TriMet of Portland, Oregon in collaboration with Google, this specification has become common for transit agencies around the world to publish their consumer facing datasets.

GTFS is split into a schedule component that contains schedule, fare, and geographic transit information and a real-time component that contains arrival predictions, vehicle positions and service advisories. Static GTFS consists of routes, trips, stop_times, stops and calendar as mandatory tables. There are also other optional tables such as fares and frequencies. Real Time GTFS (gtfs-rt) consists of trip updates, service interruptions etc.

Reading in GTFS files

Because GTFS are regularly updated (usually semi-annually) and published on transit agency’s website, it is a good idea to get the latest schedule. Fortunately, Mobility Database has a catalogue of various GTFS feeds and their source locations. In this tutorial, I am going to use Metro St. Louis GTFS feed.

I am going to use the tidytransit package. read_gtfs reads the zipfile and converts it into a bunch of tables.

In the following code, I am showing how to download the latest GTFS files. However, I am going to use an archived copy of that feed for consistency.

Analysing Service Patterns

The GTFS reference specifies that a “service_id contains an ID that uniquely identifies a set of dates when service is available for one or more routes.” A service could run on every weekday or only on Saturdays for example. However, feeds are not required to indicate anything with service_ids and some feeds even use a unique service_id for each trip and day. Service patterns can be used to find a typical day for further analysis like routing or trip frequencies for different days.

Accessibility as Cumulative Opportunity

While it is useful to think of accessibility as frequency of transit at a particular location, that indicator does not tell us much about the system level accessibility. While a specific bus station might have frequent departures, it may be on a line that is broadly disconnected from the rest of the transit system (e.g. connected to other lines that have significant wait times). It is thus useful to measure accessibility as opportunities that can be accessed within a travel budget (say 45 minutes). To do compute these, it is useful to figure out how much area can be covered within 45 min of travel time.

It is reasonably straightforward to figure out how much area can be covered by foot using routing engines such as OSRM. The tricky bit is to figure out how much time is spent waiting at transit stations before boarding the buses/trains and during transfers.

Typically, accessibility is measured for centroids of population centers (block groups e.g.). However, any origin set should be fine. I select the the three counties for the analysis (St. Clair in IL and St. Louis City, St. Louis County in MO)

transitstops <- stlouis_gtfs$stops

get_centroids <- function(state, county) {
  centroids <- tigris::block_groups(state = state, county = county, year = 2024, progress_bar = FALSE) |>
    st_centroid() |>
    st_transform(st_crs(transitstops)) |>
    select(GEOID)
  return(centroids)
}

blkgrps <- bind_rows(get_centroids("MO", c("510", "189")),
                     get_centroids("IL", "163"))

An analytical decision to make early on is to assign the origin to a nearest starting point on the transit network or to the nearest starting point on the road (foot/bike) network. It is always more computationally expensive to model both the first and last mile of travel. In this tutorial, I will demonstrate how this might be possible.

We need to operationalise a few things. Some of them are easier to precompute and some of them are easier on the fly.

  1. Travel time from each origin (block group centroid) to each destination (transit station) by foot. This is presumably time invariant, as the road network is not subject to schedules. However, this is highly dependent on the quality of the road network and appropriate information about crossings and non-pedestrian roads. I am simplifying this and simply assigning all pedestrian roads have same walk speed and non-pedestrian roads are not traversable.

  2. Travel time from each transit station to every other transit station. For the sake of practicality, we will limit the number of transfers to 3. This is highly dependent on schedules, especially when the trip starts and what time the transit reaches each stop and if there are any transfers available to other routes within the travel budget. This is time varying.

  3. The geography that can be covered from each transit stop in the remaining time after the transit trip is concluded. While, we do not know apriori how much time is remaining, we know that it cannot exceed the travel budget (45 min). So we can precompute 1 min isochrones from each transit station and select them as necessary.

  4. While we are focused on transit, it could very well be that many of the block groups may not have access to good quality transit and therefore the entire travel budget is spent on foot.Thus, we also compute the isochrones for the block group centroids.

All the steps (except the second) can be computed using routing engines such as OSRM.

What we need is the cumulative isochrone (e.g. reached within 15 min), which is the ring with its holes filled. We work in UTM 15N (EPSG:26915), because planar geometry is more forgiving of these messy polygons.

fill_holes <- function(x) {
  filled <- x |>
    st_geometry() |>
    st_transform(26915) |>
    st_make_valid() |>
    nngeo::st_remove_holes()
  return(filled)
}

How long would all the queries take?

We need these two queries for every block group and every stop. Before starting a long run, time a small sample and scale it up. OSRM moves each location to the closest road, so a location that has to move too far gets NA.

max_snap <- set_units(1, "km")

# TRUE when OSRM had to move a location too far to trust the result.
snapped_too_far <- function(snapped) {
  return(set_units(snapped$snapping_distance, "km") > max_snap)
}

one_minute_bands <- function(location) {
  snapped <- osrmTable(src = location, dst = location, measure = "duration")$sources
  if (snapped_too_far(snapped)) {
    return(NA)
  }
  return(osrmIsochrone(loc = location, breaks = seq(0, 45, 1)))
}

sample_stops <- transitstops[1:5, ]

sample_time <- system.time(
  map(seq_len(nrow(sample_stops)), function(i) {
    return(one_minute_bands(sample_stops[i, ]))
  })
)

per_location <- set_units(sample_time[["elapsed"]] / nrow(sample_stops), "s")
n_locations <- nrow(blkgrps) + nrow(transitstops)

That is one person, one location at a time, and leaves out the travel time matrix. There are two ways to do it.

Query the cloud server. You can run the full code below against the cloud server, but keep the following in mind.

  • It is a small shared machine. A long run slows everyone else down and may crash the server.
  • It can go down without notice, and a crash partway through loses whatever has not been saved. Save the results in batches as you go.
  • A very large travel time request may be refused, so keep the batches small.
  • It does not have all of the US. The snapping check above guards against locations outside its network.

Set up your own server. This is the better choice for a full run. Download the latest OpenStreetMap data for Missouri and Illinois from Geofabrik. Then run the following in a terminal to build a foot network clipped to the region and start the server (more on setting up OSRM). batches <- split(seq_len(nrow(blkgrps)), ceiling(seq_len(nrow(blkgrps)) / 100))

durations <- map(batches, function(rows) {
  table_part <- osrmTable(src = blkgrps[rows, ], dst = transitstops, measure = "duration")
  table_part$durations[snapped_too_far(table_part$sources), ] <- NA
  table_part$durations[, snapped_too_far(table_part$destinations)] <- NA
  return(table_part$durations)
})

ttmatrix <- list(durations = round(do.call(rbind, durations)))
dimnames(ttmatrix$durations) <- list(blkgrps$GEOID, transitstops$stop_id)

isochrones_for <- function(locations, ids) {
  iso <- map(seq_len(nrow(locations)), possibly(function(i) {
    return(one_minute_bands(locations[i, ]))
  }, otherwise = NULL))
  names(iso) <- ids
  return(iso)
}

blkgrp_iso <- isochrones_for(blkgrps, blkgrps$GEOID)
stop_iso <- isochrones_for(transitstops, transitstops$stop_id)

Adding the transit trip

The second part of the list above is computed using the Round-Based Public Transit Routing Algorithm (RAPTOR) for each start time. But first we need to make a transfer table. Typically GTFS should come with one that specifies the time taken to transfer between two stations (within reasonable time frame). Since we do not have it here in the St. Louis GTFS, we infer one based on distance (typically within 200 m) and a walking speed of 5 km/h.

walking_speed <- set_units(5, "km/h")

neighbours <- st_is_within_distance(transitstops, dist = set_units(200, "m"))

stlouis_gtfs$transfers <- tibble(from = rep(seq_along(neighbours), lengths(neighbours)),
                                 to = unlist(neighbours)) |>
  mutate(from_stop_id = transitstops$stop_id[from],
         to_stop_id = transitstops$stop_id[to],
         distance = st_distance(transitstops[from, ], transitstops[to, ], by_element = TRUE),
         transfer_type = 2L,
         min_transfer_time = drop_units(set_units(distance / walking_speed, "s"))) |>   # raptor wants plain seconds
  select(from_stop_id, to_stop_id, transfer_type, min_transfer_time)

The reach of one block group

We now have all the pieces. In the following code, I am going to demonstrate the extent of reach for the same block group and focus on a single start time at 6:20 AM on a weekday. The exercise below iterates over a vector of times and block groups.

travel_budget <- set_units(45, "min")

blk_start_time <- period_to_seconds(hm("6:20"))

# Trips on a single weekday within the travel budget. All the searches below share this table.
transit_stop_times <- filter_stop_times(stlouis_gtfs, analysis_date,
                                        min_departure_time = blk_start_time,
                                        max_arrival_time = blk_end_time)

# How much time it takes to reach different transit stations from the block group centroid.
travel_to_stations <- tibble(stop_id = transitstops$stop_id,
                             walk_time = set_units(ttmatrix$durations[blkgrp_id, ], "min")) |>
  filter(walk_time < travel_budget,
         stop_id %in% transit_stop_times$stop_id) |>
  mutate(earliest_departure = blk_start_time + drop_units(set_units(walk_time, "s")))

# For each station that can be reached on foot, the other stations reached by transit in the budget.
journeys_from_station <- function(stop_id, earliest_departure) {
  journeys <- raptor(transit_stop_times,
                     stlouis_gtfs$transfers,
                     stop_ids = stop_id,
                     time_range = c(earliest_departure, blk_end_time),
                     max_transfers = 3,
                     keep = "earliest")
  return(journeys)
}

has_rows <- function(x) {
  return(nrow(x) > 0)
}

# The remaining time from the travel budget, keeping the best journey to each station.
remain_time_dt <- map2(travel_to_stations$stop_id,
                       travel_to_stations$earliest_departure,
                       journeys_from_station) |>
  keep(has_rows) |>
  list_rbind() |>
  as_tibble() |>
  mutate(remain_time = to_minutes(blk_end_time - journey_arrival_time)) |>
  filter(remain_time > set_units(0, "min")) |>
  slice_max(remain_time, n = 1, by = to_stop_id, with_ties = FALSE) |>
  select(to_stop_id, remain_time)

Exercise 2: Isochrones over time and space

  • Create a function that will take start time as an argument and return the transit+walk isochrones for a block group. Use it to compute the isochrones for every 10 min for a single block group

  • Create a function that will return the isochrones for a single start time, but for all block groups.

  • Combine the two functions and create the isochrones that change over time and over space for all of St. Louis. What story can you tell about diurnal variation in accessibility.

  • Repeat this exercise for a transit system that has significant weekly and seasonal variablity (e.g. Duke/Durham)

Hint: Everything that depends on the start time or the block group in the code above becomes an argument. Each combination takes about 10 s, so try a few block groups and start times before attempting all of them.

Solution

One block group, every 10 min

function reach(block group, start time):
    end time = start time + travel budget
    keep the stop times for the date between start time and end time
    find the stops within walking distance before the end time
    for each of those stops:
        search the transit network from the time we arrive on foot until the end time
    for each stop reached, keep the journey leaving the most time on the budget
    for each stop reached, take its isochrone for the remaining time and fill its holes
    union them with the block group's own walking isochrone
    return the polygon and its area

for start time from 05:00 to 23:00, every 10 min:
    reach(block group, start time)

If no stop can be reached in time, the function should return the walking isochrone alone.

All block groups, one start time

for each block group:
    reach(block group, start time)
stack the results into one table with the GEOID and the area

Over time and space

for each start time:
    for each block group:
        reach(block group, start time)
summarise the area for each block group: median and spread across start times
summarise the area for each start time: median across block groups
map the median and the spread, and plot the area against the start time

Run this on a sample of block groups first, or in parallel. A single start time can mislead, because the area depends on how that time lines up with departures. For the block group above, the reach on foot is 21 sq km, while with transit it swings between about 40 and 65 sq km through the weekday without tracking the rush hour. A block group in the city (295101124002) ranges from about 76 to 114 sq km. So report a summary over many start times.

Conclusions

Cumulative Opportunity is only one type of accessibility measures and perhaps not even the most useful one. But the above code can be easily adapted to gravity based measures or even any other kind of time/distance decay weighting. In any case, it is important to recognise that accessibility is unevenly distributed in both space and in time. Cumulative Opportunity is as good as any in demonstrating this.

Also while GTFS is about schedules, it is important to note that real travel times on transit systems rarely conform to the schedule. It is useful to think about how real time information can be useful in understanding why transit may or may not be a viable option for different constraints of life. More importantly, the above analysis does not account for tours and has implicitly assumed trips as the basis for accessibility. Again, caution should be used to interpret these.
